# 缺陷分析 Rules

当收到缺陷描述并要求分析时，必须严格按以下流程执行：先定位根因，再给出修复方案，最后补充验证用例。禁止跳过根因分析直接给修复方案。

## 一、根因分析（Root Cause Analysis）

### 1.1 输入信息确认
在开始分析前，确认已收集以下信息：
- **缺陷描述**：标题、现象描述、影响范围。
- **复现步骤**：精确到每一步操作序列，含输入数据。
- **日志/错误信息**：完整的 error stack、console log、network 日志。
- **环境信息**：浏览器版本、OS、用户角色、数据状态。
- **代码改动上下文**：最近的 commit diff，涉及的代码文件。

如果以上信息不完整，必须标注"信息缺失"并列出缺失项，不得在信息不足时强行给出结论。

### 1.2 分析流程
1. **复现确认**：基于复现步骤，判断是否能稳定复现（必现/概率性/随机）。
2. **代码定位**：基于日志和错误信息，定位到具体代码文件、函数、行号。
3. **原因分类**：
   - 逻辑错误：条件判断错误、计算逻辑错误、状态扭转错误。
   - 数据错误：数据格式不匹配、null/undefined 未处理、类型错误。
   - 时序问题：竞态条件、异步顺序错误、回调时序错误。
   - 集成问题：API 字段变更未同步、依赖库 bug、环境差异。
4. **影响评估**：
   - 影响范围：多少用户/功能受影响。
   - 数据影响：是否有数据损坏/丢失。
   - 连锁影响：是否会触发其他功能异常。

### 1.3 根因输出格式
```
根因分类：[逻辑错误/数据错误/时序问题/集成问题]
代码位置：src/xxx/xxx.ts:行号
根因描述：[一句话描述为什么会产生该缺陷]
影响评估：[对用户、数据、其他功能的影响范围]
```

## 二、最小修复方案（Minimal Fix）

### 2.1 修复原则
- **最小改动**：只修改导致问题的代码，不做重构或优化。
- **单一修改**：一处修复解决一个根因，避免一个 patch 改多处无关代码。
- **向后兼容**：不改变已有接口的契约，不修改公共类型定义除非确有必要。

### 2.2 修复方案必须包含
- 修改文件路径及具体行号。
- 修改前代码（当前错误的代码）。
- 修改后代码（修复后的代码）。
- 修改原因说明（对应哪个根因）。

### 2.3 修复风险评估
- 此修复是否影响其他调用方？
- 此修复是否有副作用？
- 是否需要配套的数据修复/migration？

## 三、验证用例（Verification Cases）

### 3.1 必须补充的验证用例
针对该缺陷，至少补充以下三类用例：

1. **原 bug 复现用例**：
   - 确保修复前该用例能复现 bug。
   - 用例描述：[步骤] → [预期修复后行为]

2. **修复验证用例**：
   - 确保修复后该用例通过。
   - 覆盖缺陷的所有触发条件。

3. **回归保护用例**：
   - 相关功能的正常路径用例。
   - 边界条件用例（参考复现步骤中的边界值）。

### 3.2 用例格式
```
用例 ID：BUG-[缺陷编号]-[序号]
级别：单元测试/集成测试/E2E
步骤：[操作步骤]
输入：[具体输入数据/参数]
预期：[修复后的正确行为]
```

## 输出格式

缺陷分析报告按以下顺序输出：
1. 根因分析
2. 最小修复方案
3. 验证用例清单
4. 修复后回归范围（列出需要额外验证的功能点）
