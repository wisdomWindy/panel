# 需求拆解 Rules

当收到需求并要求拆解为独立可开发小模块时，必须严格按以下结构输出，禁止跨模块混合描述。

## 拆解原则

1. **单一职责**：每个模块只做一件事，有明确的输入/输出边界。
2. **依赖最小化**：尽量减少模块间依赖，优先设计无依赖模块。
3. **可独立验证**：每个模块必须能独立测试，有自己的验收标准。
4. **优先并行**：识别无依赖模块标记为"适合并行开发"。

## 每个模块必须包含的信息

### 模块名称
简洁描述模块功能，格式：`[模块名称] - 一句话功能说明`

### 输入（Inputs）
- 数据输入：API 参数、数据库表、文件、消息队列等。
- 配置输入：环境变量、feature flag、配置文件。
- 上游模块输出（如有依赖）。
- 每一项标明是否必需（required/optional）。

### 输出（Outputs）
- 数据输出：API 响应、数据库写入、文件生成、消息发布等。
- 副作用：日志、监控指标、缓存更新。
- 每一项标明格式和存储位置。

### 依赖（Dependencies）
- 外部服务：第三方 API、内部微服务、数据库。
- SDK/库：npm 包、框架版本。
- 上游模块：必须先完成的模块。
- 标注每个依赖的就绪状态（已可用/待开发/需采购）。

### 验收标准（Acceptance Criteria）
- 至少 3 条可验证的验收条件。
- 每条条件必须是可通过测试用例验证的。
- 区分正常路径验收和异常路径验收。

### 并行开发标记（Parallelizable）
- `是`：与所有其他模块无数据依赖，可立即开始。
- `有条件`：依赖于模块 X，但 X 的接口已定义可 mock，可并行。
- `否`：必须等待上游模块完成。

## 输出格式

### 模块依赖图
用文本描述各模块间的依赖关系（DAG），标注关键路径。

### 模块清单
按推荐开发顺序排列，每个模块包含上述六项内容。

### 并行开发建议
给出最优并行分组方案，说明每组可以同时启动的原因。
