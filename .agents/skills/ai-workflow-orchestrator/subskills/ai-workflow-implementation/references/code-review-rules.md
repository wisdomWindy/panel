# Code Review Rules

当收到代码改动要求 Review 时，必须严格限定在以下五个维度，禁止发散到代码风格、命名偏好、个人审美等无关优化建议。

## 审查维度（五维度强制审查）

### 1. 缺陷（Defects）
- **逻辑错误**：条件判断、循环边界、类型转换、null/undefined 处理。
- **状态管理错误**：状态未初始化、状态竞争、状态未清理。
- **异步处理错误**：Promise 未处理拒绝、async/await 缺失、竞态条件。
- **资源泄漏**：事件监听未移除、定时器未清除、WebSocket 未关闭、Subscription 未取消。

对每个发现的缺陷：
- 说明触发条件。
- 给出复现步骤（至少 2 步）。
- 标注严重程度（P0 崩溃/数据丢失、P1 功能不可用、P2 体验缺陷）。

### 2. 回归风险（Regression Risks）
- 改动是否影响了共享模块/工具函数（被多处引用的代码）。
- 字段重命名、接口签名变更是否有兼容性处理。
- 默认值变更是否影响已有行为。
- 样式改动是否影响其他页面（全局 CSS/Tailwind 配置变更）。
- 依赖版本升级是否引入 breaking change。

对每个回归风险：
- 标注影响范围（全局/模块级/页面级）。
- 列出需要重新验证的已有功能。

### 3. 边界条件（Boundary Conditions）
- 空值/NULL：API 返回 null、数组为空、字符串为空。
- 极值：数字溢出、数组索引越界、字符串长度超限。
- 特殊字符：SQL 注入、XSS、Markdown/HTML 转义。
- 并发：同一用户多次点击、多个请求同时到达。
- 网络边界：断网、慢网络、服务端 5xx 错误、超时。

对每个未处理的边界条件：
- 说明具体场景。
- 建议最小处理方式（不需要完整防御体系）。

### 4. 权限问题（Permission Issues）
- 前端权限检查是否可被绕过（前端隐藏 ≠ 安全控制）。
- 接口是否有服务端权限校验。
- 是否有越权风险（水平越权/垂直越权）。
- 敏感数据是否暴露在客户端（API 响应中泄露不应返回的字段）。
- Token/Session 管理是否正确（到期处理、刷新机制）。

### 5. 测试缺口（Test Gaps）
- 新增代码是否有对应的测试用例。
- 修改的逻辑路径是否覆盖：
  - 正常路径（happy path）
  - 异常路径（error path）
  - 边界值（boundary values）
- 是否存在未测的异步流程。
- 是否存在未测的 UI 交互（用户操作序列）。

## 输出格式

### Review 结论
结论分三档：
- **Approve**：未发现上述任何问题，代码可合并。
- **Approve with Comments**：存在建议项但非阻塞，标注"建议"。
- **Request Changes**：存在阻塞问题（defect/regression/permission），必须修复后重新 review。

### 问题清单
每一项问题必须包含：
- 维度标签（缺陷/回归/边界/权限/测试）
- 严重程度（仅缺陷维度：P0/P1/P2；其余维度：阻塞/建议）
- 具体代码位置（文件路径:行号）
- 问题描述
- 修复建议（最小改动方案）
