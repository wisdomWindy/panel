# 技术方案 Rules

当收到需求要求基于现有项目结构给出技术方案时，必须严格遵循"最小改动"原则，按以下六个维度输出，禁止引入不必要的重构或过度设计。

## 原则

- **最小改动**：优先复用现有模块、组件、工具函数，只在必要时新增文件。
- **向后兼容**：不得破坏已有接口和数据格式，如有 breaking change 必须明确标注。
- **单一关注点**：每个改动只解决一个问题，不为"可能的需求"预留扩展。

## 技术方案必须包含的信息

### 1. 涉及文件（Affected Files）
按类别列出所有需要修改或新增的文件：

| 文件路径 | 操作 | 改动说明 |
|---------|------|---------|
| src/xxx/xxx.ts | 修改 | 添加 xxx 方法 |
| src/yyy/yyy.vue | 新增 | 新增 xxx 页面 |

- 标注每个文件的操作：新增/修改/删除。
- 禁止"顺便改"与需求无关的文件。

### 2. 接口字段（API & Data Contracts）
- 新增/修改的 API 端点：请求方法、路径、请求体/响应体结构。
- 新增/修改的数据模型：表名、字段、类型、约束、索引。
- 组件 Props/Emits 定义（Vue 项目）。
- Pinia Store 的 state/actions/getters 变更。

### 3. 数据流（Data Flow）
描述数据如何从入口流动到最终输出：
- 用户操作 → 前端事件 → API 调用 → 服务端处理 → 数据库读写 → 响应返回 → UI 更新。
- 标注每一步可能的失败点和容错策略。
- 区分同步流和异步流（WebSocket、轮询、事件总线）。

### 4. 异常处理（Error Handling）
对每种异常场景给出处理策略：
- 网络异常：重试策略（次数、间隔、退避算法）。
- 数据异常：校验规则、默认值、降级逻辑。
- 并发冲突：乐观锁/悲观锁/队列化。
- 超时处理：超时时间、超时后行为（重试/降级/报错）。
- 权限不足：前端隐藏/禁用 vs 后端拦截。

### 5. 回归风险（Regression Risks）
- 列出受影响的已有功能列表。
- 对每个受影响功能评估回归风险等级（高/中/低）。
- 标注需要执行的回归测试用例。

### 6. 实现检查清单
- [ ] TypeScript 类型定义完整
- [ ] 错误处理覆盖所有异常场景
- [ ] 日志埋点覆盖关键路径
- [ ] 单元测试覆盖核心逻辑
- [ ] 集成测试覆盖数据流
- [ ] i18n 文案已添加
- [ ] 文档更新（如需要）

## 输出格式

技术方案文档需包含以上六个章节，每章不得跳过。方案末尾附"风险提示"章节，汇总所有高风险的改动点。
