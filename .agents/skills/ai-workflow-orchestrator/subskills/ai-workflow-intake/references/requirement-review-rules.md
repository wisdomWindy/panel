# 需求 Review Rules

当收到需求文档并要求 review 时，必须严格按以下七个维度逐项分析，禁止跳过任何维度。

## 1. 目标（Goal）
- 用一句话提炼需求的核心目标。
- 判断目标是否可量化（有明确的 KPI/指标）还是仅定性描述。
- 如果目标不可量化，标记为待确认事项。

## 2. 范围（Scope）
- 画出需求的功能边界：哪些功能属于本期，哪些明确不包含。
- 检查是否存在范围蔓延（scope creep）的迹象。
- 识别与现有功能的交叉或重叠，标记冲突点。

## 3. 数据来源（Data Source）
- 逐一列出需求中涉及的所有数据字段及其来源。
- 标注每个数据源的类型：用户输入、第三方 API、内部数据库、实时流、离线计算等。
- 对每个外部依赖的数据源，确认其 SLA 和可用性。
- 对新引入的数据字段，标注是否需要数据迁移或回填。

## 4. 权限（Permissions）
- 列出所有涉及的角色和操作。
- 检查每个操作的权限模型是否已定义（RBAC/ABAC/无）。
- 标记缺少权限定义的敏感操作。
- 检查权限边界是否清晰（租户隔离、用户间数据隔离）。

## 5. 异常场景（Edge Cases）
- 列出至少 5 种异常场景及预期行为。
- 覆盖：空数据、超大量数据、并发冲突、网络异常、超时、数据格式错误、用户中断操作。
- 对每个异常场景，判断当前需求是否定义了 fallback 行为。
- 标记未覆盖的异常场景。

## 6. 测试点（Test Points）
- 基于需求提取可验证的测试点。
- 区分：单元测试级别、集成测试级别、端到端测试级别。
- 对每个测试点标注优先级（P0/P1/P2）。
- 检查是否存在自动化测试覆盖缺口。

## 7. 上线风险（Launch Risks）
- 识别上线相关的技术风险和业务风险。
- 评估回滚方案是否可行（是否有数据兼容性问题）。
- 标注是否需要灰度发布或 feature flag。
- 评估对已有用户和数据的 blast radius（影响半径）。

## 输出格式

### 待确认问题（Pending Questions）
列出所有标记为待确认的问题，按优先级排序，每条包含：
- 维度标签（目标/范围/数据/权限/异常/测试/风险）
- 问题描述
- 影响评估（阻塞/高风险/建议）

### Review 结论
- 通过（无阻塞问题）
- 有条件通过（存在建议项）
- 不通过（存在阻塞问题，退回上游）
